## Test layers

1. Extend `apps/web/tests/research.spec.ts` for the changed main workflow and keyboard diagnostic behavior. Update only assertions whose visible behavior changes and keep the real backend fixture.
2. Add focused regressions for new navigation and draft behavior, stale response handling, and shared run tracking where the existing browser flow cannot catch the failure. Prefer deterministic API delay or failure fixtures for race conditions.
3. Run web type checking, the Next.js production build, Playwright, and the existing CI regression gates relevant to touched code. If a phase changes API schemas or engine behavior, treat it as a separate scoped change and run the associated contract and engine gates.
4. Review same-state screenshots at desktop, laptop, and narrow widths. Record keyboard, focus, chart readability, long labels, and empty and error states alongside the images. Use screenshots to verify layout and browser interaction to verify behavior.

## Rollout checks

Land coherent slices with the current bookmarks and UI workflows usable at each merge. Use a single release gate for every redesigned screen, including the pinned baseline and metric deltas. Begin with a fresh-library smoke test, then verify an existing library still opens saved strategies, revisions, datasets, and runs. Include narrow layout and theme checks before release. Update the existing browser guide and design handoff with the terminal workflow. [Browser guide](../../browser.md) · [Existing design handoff](../editor-visualizer/README.md)

If a slice fails its acceptance criteria, revert its frontend commits and retest the preserved direct routes with the existing library. If the terminal introduces stored UI preferences, use a versioned key and allow the workspace to open with defaults when that state is missing or invalid.
